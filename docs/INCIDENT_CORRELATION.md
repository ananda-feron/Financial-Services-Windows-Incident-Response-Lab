# Incident Correlation and Investigation

## Phase 3 boundary

This phase implements `alerts → incidents → timeline → evidence`. It does not extract IOCs, execute response actions, calculate detection performance, or provide a dashboard.

## Deterministic correlation

Alerts are evaluated chronologically and join the most recently active compatible incident only when all of these conditions hold:

1. Hostnames match case-insensitively.
2. Usernames match case-insensitively. Two unresolved usernames may match each other, but an unresolved user never matches a named user.
3. The gap from the incident's latest alert is no more than 15 minutes by default.
4. ATT&CK activity is related: identical technique, identical tactic, or one of the documented tactic transitions below.

Supported cross-tactic relationships are Execution ↔ Credential Access, Persistence, Discovery, or Lateral Movement, plus Credential Access ↔ Lateral Movement.

This is a transparent lab heuristic, not a universal production correlation policy. It deliberately avoids merging alerts solely because they share a technique or dataset.

## Severity

Incident severity is the highest linked alert severity:

```text
critical > high > medium > low
```

A critical alert therefore produces a critical incident. The algorithm is intentionally simple and auditable; business criticality and impact scoring belong in a later phase.

## Persistence and evidence

- `incidents` stores case-level state and first/last-seen times.
- `incident_alerts` references existing `alerts` rows.
- `incident_evidence` references existing `events` and `alerts` rows.
- `notes` stores analyst reasoning with author convention and timestamp.
- Timeline entries are generated by joining incidents to alerts and events in event-time order.
- Original XML is read from the existing event only when evidence is requested.

No alert or raw event is copied into the incident tables.

## Run

Correlate alerts and generate focused static investigation pages:

```bash
python -m incidents.engine --render-dir reports/generated/incidents
```

Add an analyst note:

```bash
python -m incidents.notes INC-XXXXXXXXXX --body "PowerShell activity preceded LSASS access on the same host."
```

Regenerate the page after adding a note. Each timeline item has an expandable evidence section that retrieves its referenced original XML during rendering.

## Investigation status values

`NEW`, `TRIAGING`, `INVESTIGATING`, `CONTAINED`, `RESOLVED`, and `CLOSED` are valid model states. Newly correlated incidents begin as `NEW`; response-action and lifecycle-transition workflows are intentionally deferred.
